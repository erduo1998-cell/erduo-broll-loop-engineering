# v1.0.0 Production Loop Design

## 目标与边界

v1.0.0 从 v0.9.2 原地升级已验证的 B-roll 生产闭环。它没有新增并行的 fast pipeline，也没有删除 Director、Assets、多 Builder、HyperFrames、Remotion、Hybrid、可编辑源码、素材来源或冻结媒体装配边界。

本版修正四个默认合同：短语义镜头不再等于一个 Builder；视觉方向在批量制作前由真实动态代表场景锁定；普通单后端冻结媒体不再默认使用巨大的 4K FFV1；motion/layout 与生产计量不再依赖全片重复扫描和默认逐帧 PNG。

自动测试、schema 和短媒体 fixture 只能证明工程合同。它们不能证明真实 180 秒任务达到耗时、目录或 Token 目标，也不能替用户作审美决定。

## 正常生产状态机

```text
Parent
→ Director：narrative envelope、visual system、短语义 Shot Recipes、三个代表场景
→ Runtime Plan v3：后端选择、Builder 工作包、Lead assignments
→ Assets：一次闭合素材与字体
→ Lead Builder：三个真实动态代表场景 + 每实际后端共享视觉源码
→ Director witness
→ 用户 visual lock：approve / revise / skip
→ 其余 Builders 并行完成工作包
→ H.264 或显式升级的冻结 unit
→ 脚本装配完整 preview
→ Director 完整动态 witness
→ 用户批准完整 preview
→ 身份复核与 Master 交付
```

`Lead Builder` 是现有 HyperFrames 或 Remotion Builder 的 assignment 模式，不是新 Agent 类型。Runtime Planner、Integrator 和 Render 阶段 Skill 只保留历史记录兼容，不进入正常 v1 路径。

## Shot 与 Builder 工作包

Shot Recipe v3 默认把一个完整语义镜头控制在约 5–12 秒。超过 15 秒仍可存在，但必须说明为何内容需要持续发展；背景循环、粒子、能量线或大字停留不能单独证明必要性。

Runtime Plan v3 独立处理 `shots` 与 `authoringUnits`：

- 每个 shot 在时间线上只出现一次，继续使用 SRT 整数毫秒并连续覆盖零到末句。
- unit 不跨 backend block、不跨不连续时间，也不拆开必须在同一 runtime 内完成的 live transition。
- 普通连续短镜头按后端、共享组件、素材依赖、接缝和工作复杂度确定性聚合；一个 unit 通常可含约 5–8 个镜头。
- 约 180 秒、单后端、普通复杂度任务以 2–3 个 Builder 为规划目标，不是强制数量。
- `authoring.solo`、复杂 3D、独占状态、重素材和强 live transition 可以形成单独 unit。

Builder assignment 只暴露本 unit Recipes、相邻 seam、共享 artifact、素材/字体计划和实际命中的少量 reference；`contextMode` 必须为 minimal，不继承父任务完整历史。

## Representative Scenes 与 Visual Lock

Director 写出严格的 `representative-scenes.json`，恰好选择三个不同 shot：

- `opening`：开头的第一印象和世界建立；
- `information-dense`：文字、关系或高信息密度压力；
- `late`：后段延续性、收束或结尾适用性。

每项记录选择理由及它覆盖的构图、文字、材质和运动问题，不机械选择前三镜。

Lead Builder 交付三个真实动态场景，并建立可导入的视觉母体：本地字体和层级、栅格与安全区、背景/灯光/材质/深度、标题/数字/标签/关系排版，以及进入、强调、状态变化、退出和 readable hold motion token。

共享源码按 runtime 隔离。单后端生产只有一个母体；Hybrid 只共享运行时中立 token，HyperFrames 与 Remotion 各自产生自己的最小实现源码，不能跨后端导入。

`visual-lock.json` 绑定代表场景媒体、共享源码 manifest/source identity、字体/资产、Director 具体 witness 和用户决定：

- `approved`：允许普通 Builder fan-out；
- `revision-required`：返回原 Lead Builder 定点修改；
- `skipped`：用户明确承担方向漂移风险后继续；
- `pending`：禁止普通 Builder fan-out。

共享母体是可复用语言，不是整片模板。后续 Builder 仍需为每个 Recipe 原创内容、构图和运动。

## 冻结媒体与装配

默认 production profile 仍为 3840×2160、30 fps、静音、H.264 MP4 Master。v1 普通单后端 unit 的默认冻结策略为：

- container：MP4；
- codec/encoder：H.264 / `libx264`；
- preset：`medium`；
- CRF：`12`；
- pixel format：`yuv420p`；
- BT.709、TV range；
- 约两秒固定 GOP，关闭 scene-cut keyframe；
- class：`visually-lossless`。

这里的 `visually-lossless` 是生产合同名称，CRF 12 是高质量工程策略，不是审美证明。短 fixture 已验证 H.264 unit、H.264 concat、最终单次重编码和显式 FFV1 都可完整解码；它不是 180 秒真实性能证据。

`create-production-profile.mjs --mezzanine-format ffv1-mkv --mezzanine-reason <原因>` 可显式升级为 FFV1 `yuv444p10le` lossless。没有原因的 FFV1 新 profile 被拒绝。Hybrid、透明、后期再编码或真实无损交换可以使用该升级；历史 v0.9 FFV1 profile 继续按 legacy 合同读取，不被静默改写。

Builder 仍交付编辑源码、source manifest/source identity、`block-media.json`、媒体 hash、FFprobe 和完整解码事实。Assembler 按 plan 顺序读取 unit，preview 最高 1080p、`veryfast / CRF 22`；交付阶段从未变更的冻结 unit 重新编码完整规格 `medium / CRF 16` Master，不复制 preview。

Preview identity 绑定 plan（其中包含 representative-scenes identity）、narrative envelope、visual system、全部 unit contracts、媒体/source identity 和 preview bytes。任一绑定输入漂移都要求生成新 preview 并重新批准。

## 分层 Motion/Layout

默认检查顺序为：

1. Recipe beat 边界、readable hold、场景切点和必要 sampling；
2. 发现跳变、越界、碰撞、遮挡、未 settle、可读性或 development 缺口时，只升级异常时间窗口；
3. 精密 connector/path、Canvas/WebGL、用户明确要求的场景继续使用高密度或逐帧证据；
4. 通过时不生成静帧、clip 或全片逐帧 PNG。

无法可靠测量的主要发展必须保留为 `unmeasured`，不能从源码或截图推断成通过。检查只处理可测的时间、运动、布局和图解底线，不评分审美。

## Provider-neutral Production Metrics

Parent 可用 `record-production-event.mjs` 写入结构化 `production-events.ndjson`，再由 `collect-production-metrics.mjs` 生成公开安全的 `production-metrics.json`。计量包含：

- 阶段开始、结束和墙钟耗时；
- Director、Assets、Builder、revision 调用次数和 full-history 计数；
- authoring unit、镜头数和时长；
- 单次生产目录扫描得到的文件数、字节、扩展名、类型和最大目录；
- render、trace、full-decode、hash-scan 次数与处理字节；
- 失败、重试、责任阶段和责任 unit；
- 可选 Parent/host 提供的 input、cached input、non-cached input、output Token。

没有可靠 Token 事实时全部写 `unknown`，不估算。脚本不读取宿主私人 session 路径，不接收自由文本事件，也不把绝对 production path 写入公开记录。

## 画面理解合同

每个 Recipe 先明确观众第一眼看到的具体锚点、发生的动作和最后得到的结果。抽象隐喻仍允许，但必须由立即可读的对象、关系、状态或空间变化承载；不能只剩抽象材质、能量线或巨型文字。

屏幕文字只保留真正需要读的少量内容，输入为中文时优先中文；英文只用于品牌、专名或真实内容需要。长镜头由内容发展驱动，共享视觉世界至少保留多种构图家族。

Director witness 必须返回具体 `shotId`、可观察问题和返修目标。Agent 不使用审美分数，也不能以 schema、lint、截图、短 fixture 或“生成成功”宣布审美通过。

## 兼容性

- Shot Recipe v1/v2 与 Runtime Plan v1/v2 继续按声明读取和验证；新生产默认写 v3。
- 历史 run 不追溯改写，也不会因旧合同自动获得 visual lock、共享源码或轻量媒体声明。
- 标准 Skill 包与完整环境包继续包含同一份项目 Skill；安装、doctor、升级和卸载合同不因 v1 生产状态机而改变。
- HyperFrames 与 Remotion 是独立 backend；不承诺源码互转、任意既有项目兼容或视觉一致。
- Windows、剪映/CapCut GUI 和跨机器 Remotion HTML-in-canvas 仍按支持矩阵保持未验证或有限支持。

## 发布前仍需完成的真实证据

v1 代码和自动测试完成不等于正式发布验收完成。发布前仍需：指定 IP Strategist 同 SRT 的全新约 180 秒生产、三个代表场景时间、首次完整 preview 时间、目录/文件分类、Agent/返修、媒体操作、可得 Token、连续覆盖/来源/源码/身份/完整解码，以及耳总对 v1、v0.9.2 和对照 preview 的最终选择。

在这些事实落盘前，公开结论只能是“v1 工程合同已实现，真实长片性能与审美待验收”。
