# v1.0.1 PR 规格：减负、动画纪律与镜头直出

## PR 标题

`refactor: make v1 production shot-native and remove agent proof work`

## 一句话目标

保留 Director、Assets、Lead 和多 Builder 的创作分工，但把检查工具、证据文件、媒体合同和重复读文档从子 Agent 身上移走；让每个最终分段镜头都从自己的运行时源码直接渲染，并用真实的 HyperFrames / Remotion 生产证据约束“双后端”承诺。

## 为什么必须改

v1.0.0 的真实 179.866 秒实测没有达到生产目标：首次完整 preview 为 242.05 分钟，Lead 为 62.90 分钟，三个 production Builders 为 88.14 分钟。目录体积已经下降，但时间和画面质量仍不合格。

日志进一步说明，这不只是“模型写动画慢”：

- Lead 和 Builder 都承担了本应由仓库脚本完成的截图、轨迹、逐帧扫描、hash、FFprobe、decode、manifest 和证明工作。
- U001 在异常后检查全部 2112 帧；U002 又自行编写采集脚本并检查 1061 帧。它们不是更严格的创作，而是每个 Agent 重建一次检查系统。
- motion lint 把“长时间没有变化”当成缺陷，诱导 Builder 补入无意义的持续变化，直接制造动画积压、无法稳定和焦点竞争。
- Lead 只看到三个代表镜头，却输出容易被 Builder 当成整镜头模板的共享母体；Builder 再把不同内容填进同一表现形式。
- `animation-craft.md` 虽然被各层读取，但真正写源码时已经被大量上下文和工具输出冲淡。重复读取既花 Token，也不能保证执行。
- 本次运行的 `runtime-selection.json` 明确是 `selectedRuntime=hyperframes`、`selectionSource=explicit`，不能据此说 auto 自然选择了 HyperFrames，也没有证明 Remotion 完整生产闭环。
- 当前 Builder 输出 3 个 44–70 秒 unit，最终镜头文件再从 Master 切割；这不符合后期需要的“每个语义镜头直接渲染为最终分段文件”。

## 本 PR 不做什么

- 不取消 Lead。Lead 保留，但职责收窄为视觉语言、动画纪律和三种不同构图的真实样片。
- 不增加一条并行的 fast pipeline；直接修改默认流程。
- 不让 Director 重新观看全片动态视频。默认视觉检查改为逐镜头的少量语义采样。
- 不要求每个镜头机械展示十二原则，也不把十二原则做成打分表。
- 不通过降低分辨率、减少镜头或跳过完整解码伪造提速。
- 不保证 HyperFrames 与 Remotion 源码互转或画面逐像素一致。

## 新的默认流程

```text
Parent
→ Director：Shot Recipes + 紧凑全片动画地图
→ Runtime Plan：按镜头真实能力选后端，聚合 authoring units
→ Assets：一次闭合素材与字体
→ Lead：三种不同内容关系的代表镜头 + 视觉/运动原语
→ 用户可选代表镜头 visual lock
→ Builders 并行创作各自 unit 内的多条镜头
→ Parent 标准脚本按 shot 直接渲染、检查并生成合同
→ Parent 从已验证 shot 文件装配低成本整条 preview
→ 用户看 preview；最终默认交付有序 shot 文件，整条 Master 可选
```

`authoring unit` 只用于减少 Agent 数量和共享上下文；它不再决定媒体边界。媒体边界永远是语义 shot。

## 1. 子 Agent 不再建立检查工具或证明自己

### Lead / Builder 允许做的事

- 创作和修改可编辑源码。
- 调用 Parent 指定的唯一标准命令。
- 根据标准命令返回的少量具体失败项定点修复画面。
- 在 handoff 中只写真实未解决问题，不写“我读了什么”“我如何证明通过”。

### Lead / Builder 禁止做的事

- 新建 capture、trace、lint、截图、逐帧扫描、hash、FFprobe、decode、manifest 或 receipt 脚本。
- 为通过 lint、提高轨迹变化量或证明“画面持续发展”补无意义运动。
- 对通过的镜头继续做密集扫描或全帧证据。
- 手工编写媒体合同、hash、探测结果或“通过证明”。
- 阅读标准检查脚本源码后再复刻一份。

仓库测试必须拒绝 production unit 中出现 `capture*.mjs`、`trace*.mjs`、`verify*.mjs` 等自建证据工具。确有新检测能力时，只能由维护者加入仓库统一脚本和测试，不能由生产 Agent 临时发明。

### Parent 统一承担

- 渲染、抽帧、必要窗口升级、FFprobe、完整解码、hash。
- source identity、shot media contract、compact receipt 和失败摘要。
- 逐镜头输出命名、排序、连续覆盖和 preview 装配。
- 机械失败时只返回 `shotId + 时间点/窗口 + 缺陷类型 + 证据路径`；通过时只返回一行摘要。

默认检查不得生成逐帧 PNG，也不得把长轨迹日志塞回 Agent 上下文。只有命中跳变、越界、遮挡、未 settle、复杂 connector/path 或用户明确要求时，才升级对应的短窗口。

## 2. 去掉各层级重复读文件

### 子 Agent 默认只得到

1. 自动注入的本角色动画宪法；
2. 本次 assignment packet；
3. 本 unit 的 Recipes 和相邻 seam；
4. 已闭合的字体/素材清单；
5. 实际命中的最多 0–2 个专项 reference 片段。

Director、Lead 和 Builder 不再把以下文件作为启动必读：父 `SKILL.md`、其他阶段 `SKILL.md`、`animation-craft.md`、`visual-craft.md`、`motion-layout-lint.md`、schema 全文、validator 源码、完整 catalog、未选后端文档。

脚本可以被调用，不等于子 Agent 必须阅读脚本。Assignment packet 必须带齐输入、命令和输出位置，不能让 Agent 为找路径重新遍历仓库。

### 角色规则的注入方式

每个角色保留一份短小的规则真源，由生成脚本同步为：

- Codex 可继承的 `AGENTS.md`；
- Claude Code 可继承的 `CLAUDE.md`；
- Parent 创建子 Agent 时直接注入的 role prompt；
- Recipe 和正式源码制作之间不超过 8 行的执行锚点；
- 上下文压缩后的固定恢复字段。

不能把“Agent 是否主动打开并记住文件”当作保障，也不要求 Agent 复述规则或提交阅读回执。角色文件必须进入安装包，package allowlist 和 stage 文件结构测试同步更新。

## 3. 角色动画宪法

完整历史和解释留在 `animation-craft.md`；下面的硬规则直接注入角色，不能让子 Agent 另行读取。

### Director

1. 每镜只定义一个核心表达和一个主要视觉动作。
2. 先定义起始、关键转折、结果和可读停留，再描述中间运动。
3. 每个节拍明确当前焦点；背景和次要动作不得争夺焦点。
4. 重要变化可以有短预备信号，但不能给所有元素机械加弹跳或缩放。
5. 每组内容必须明确进入、停留、替换或退出，禁止只进不出。
6. 次要动作必须说明它支持哪个主动作；无法说明就删除。
7. Timing 由语义、阅读量、重量和情绪决定；稳定停留是合法状态。
8. 有机运动可使用弧线，机械运动可使用直线；不能统一套同一运动。
9. 每镜只使用真正有帮助的原则，不追求十二原则全覆盖。
10. Recipe 描述内容关系和关键状态，不指定固定模板。

### Lead

1. 阅读紧凑全片动画地图，检查相邻镜头是否重复同一构图、入场和节奏。
2. 三个代表镜头必须覆盖至少三种明显不同的内容关系和动画组织方式。
3. 统一字体、色彩、材质、运动重量和工具，不统一构图和动画路径。
4. 共享源码只提供 token、视觉原语、运动原语和基础组件，禁止交付“填内容”的整镜头模板。
5. 任一时刻只有一个主要焦点和主要动作。
6. 附属动作必须由主动作引起，幅度更弱、稍晚结束并最终稳定。
7. 检查所有元素组的进入、停留、替换或退出，禁止不断叠加。
8. 代表镜头必须有清楚结果和可读停留，禁止永久漂浮、呼吸或循环。
9. 检测规则与创作判断冲突时，不能改镜头迎合错误检测，应报告检测规则问题。
10. 不得重写项目已有的截图、轨迹、渲染和证明工具。

### Builder

1. 写源码前从 Recipe 重建起始、转折、结果和停留状态。
2. 一个节拍只能有一个主要焦点和动作，其余动作只能支持它。
3. 每组元素必须有 `hidden/enter/hold/exit` 或 `replace` 生命周期。
4. 新内容进入前必须决定旧内容保留、降级、替换还是离场，不能默认全部积压。
5. 主动作需要时使用短预备信号，完成后必须稳定；不能给每个小动作套 anticipation。
6. 跟随和次要动作必须由主动作引起、幅度更小且最终停下。
7. 路径、速度和缓动必须符合对象材质，禁止无因变向。
8. 次要动作一旦遮挡主角、降低阅读性或制造第二焦点，立即删除。
9. 默认静止；只有语义需要才持续运动。禁止为了通过 lint 补运动。
10. 不得因为共享组件存在就复用同一构图和动画模板。
11. 不得重新发明检查、截图、轨迹或渲染工具。

这些规则来自 Frank Thomas 与 Ollie Johnston 1981 年《Disney Animation: The Illusion of Life》中的十二项基本原则，再针对信息图形和 UI 动画转译。书目信息可由 [Disney Publishing](https://books.disney.com/book/the-illusion-of-life/) 核对；原则原始标题和顺序可由 [Duke University 讲义](https://users.cs.duke.edu/~bdonald/Teaching/Previous/Animation/Papers/principles.pdf) 交叉核对。原始名称是 `Slow In and Slow Out`，不要在规则真源中改写成 `Ease In and Ease Out`。

## 4. Lead 的职责边界

Lead 保留，因为它要在批量制作前回答“这个世界怎么长、怎么动”。但 Lead 不再负责建立生产证明系统，也不能把三个代表镜头变成全片模板。

Director 额外输出紧凑的 `motion-map.json`，每镜只含：

```json
{
  "shotId": "S01",
  "contentRelation": "compare|process|state-change|spatial|character|other",
  "primaryAction": "一句话",
  "compositionFamily": "一句话",
  "entryFamily": "一句话",
  "rhythm": "calm|progressive|impact|mixed",
  "settleMs": 1200
}
```

Lead 用它检查全片重复和动画章法，但不读取其余 17 镜的完整 Recipe，也不审查全片动态视频。代表镜头选择必须覆盖不同 `contentRelation`、`compositionFamily` 和 `rhythm`；无法满足时由 Director 重选，不能拿同一模板换文字。

Lead 的完成条件仅为：三条直接可渲染代表镜头、共享视觉/运动原语、标准检查无具体失败、用户选择 approve/revise/skip。不得以证据文件数量作为完成度。

### 从 14 段参考成品提取的防低级错误规则

参考成品的 14 段分别使用安装因果链、官网证据、调用链、三问、承重隐喻、输入输出桥、物料沉降、原料重组、Dashboard 聚焦、表格结论、筛选契约、四输入流程、路径问题和资源 CTA 等不同表现。PR 不复制其暗色卡片风格，只把共同章法写进角色规则：

- 先建立对象和当前状态，再让它发生变化；对象与结论不能同时凭空出现。
- 一镜只保留一条主因果关系；多条线可以存在，但都必须服务同一语义。
- 后续动作必须由前一动作触发，遵循 `准备 → 主动作 → 依赖动作 → 落定`。
- 新元素进入前先分配空间，并决定旧元素保留、降级、替换还是退出。
- 界面/表格/截图使用机械裁切和移动，不弹跳；纸张/卡片可有有限惯性；重物停止更硬；文字和 Logo 默认不挤压变形。
- 每镜只有一次最强动作，其他动作必须低于它，不能每张卡都发光、弹跳和旋转。
- 涉及网页和数据时，真实证据是主体：先给上下文，再等比聚焦真实字段，不伪造、不遮挡、不把整页缩成不可读小卡片。
- 连接线必须有真实起点和终点，不能悬空，也不能穿过文字、卡片或真实 UI。
- 可见容器必须承载信息；不得出现空框、空胶囊、重复结论卡和两套同义结果。
- 最终状态由语义结果倒推，但不能把所有最终元素从第一帧开始逐项堆满。

## 5. 最终交付改成按镜头直接渲染

### 新合同

Builder 可以在一个 unit 内创作 5–8 镜，但 Parent 必须从同一份源码分别渲染每个 Shot Recipe 的最终媒体：

```text
broll-production/05-delivery/shots/
  001-S01.mp4
  002-S02.mp4
  ...
  001-S01.shot-media.json
  002-S02.shot-media.json
  delivery-index.json
```

每镜生成一份 `shot-media.json`，另有全片 `delivery-index.json`。一份 shot 合同只能绑定一个 `shotId`，至少包含：

```json
{
  "schemaVersion": "1.0.0",
  "order": 1,
  "shotId": "S01",
  "unitId": "U001",
  "srtWindowMs": {"start": 0, "end": 10400},
  "localTimeline": {"startFrame": 0, "frameCount": 312},
  "backend": "hyperframes|remotion",
  "renderTarget": {"id": "S01", "mode": "direct-runtime-render"},
  "sourceIdentity": "sha256:...",
  "recipeIdentity": "sha256:...",
  "profileIdentity": "sha256:...",
  "media": {
    "path": "shots/001-S01.mp4",
    "durationMs": 10400,
    "width": 2880,
    "height": 2160,
    "fps": 30,
    "codec": "h264",
    "sha256": "...",
    "fullDecode": "passed"
  }
}
```

`delivery-index.json` 是后期顺序真源，只记录 `order`、`shotId`、文件、绝对 SRT 窗口、前后镜和 seam 类型。媒体本地时间从 0 开始；帧数必须由绝对 SRT 边界分别换算，不能累积浮点误差。合同由仓库脚本生成，Builder 不得手写；`renderTarget.mode` 只能是 `direct-runtime-render`，不得指向 unit 或 Master 的裁切结果。

### 交付规则

- shot 数量必须等于 Recipe 数量，顺序、整数毫秒窗口和总覆盖必须一致。
- 每条 shot 独立存在、独立 FFprobe、独立完整解码；不是从 Master 再切。
- 低成本整条 preview 从这些已验证 shot 文件装配，供观看节奏和顺序。
- 高质量整条 Master 变成可选输出；默认最终交付是高质量 shot 目录。
- `broll-shot-export` 从默认流程退出，只保留历史 Master 的兼容导出，并在文档中明确标记 legacy。
- 需要跨镜头不断开的 live transition 时，Director 必须把它定义为同一个语义 shot；否则使用真实切点或匹配接力，不能暗中依赖二次切割。
- Lead 的三条代表镜头若已获批准，直接成为对应 shot 的最终源码和媒体，不得交给 production Builder 重做。

参考成品目录“千问办公-Broll-revision-v2-最终14段”的可用事实是：14 个语义镜头分别为独立 H.264 文件，均可独立解码，并保留对应可编辑源码；它证明“创作可以按 unit 聚合、交付必须按 shot 分开”是可行合同。该目录的风格不是模板，PR 只吸收边界和验收方法。

## 6. 低成本逐镜头验收

默认不让 Director 看完整动态视频，也不做全片逐帧扫描。每镜生成一张 6 格连续语义检查图：

1. opening：进入前或初始状态；
2. preparation：主要动作前的准备状态；
3. action-a：主要变化开始；
4. action-b：主要变化继续，用于发现跳变和遮挡；
5. result：结果首次完整可读；
6. settle/tail：结尾稳定状态。

六个时间点由 Recipe 的 beat 和 hold 决定，不做均匀盲采样。命中复杂动作风险时，只对该动作附近追加 3–6 张连续帧；不能升级成整条逐帧检查。

连续帧还要检查空载体先出现、悬空线后补目标、两个状态短暂重叠，以及旧元素尚未退出新元素已经撞入。正常镜头不升级为逐帧检查。

自动底线检查：

- 文件存在、时长/帧数/分辨率/fps/编码正确并完整解码；
- 无黑屏、丢字体、核心内容越安全区、明显文字遮挡和非预期空画面；
- 每个主要元素存在进入后的去向，结尾没有旧元素积压；
- result 可读，tail 有稳定区间；静止本身不算失败；
- 同一时刻没有两个同等强度主焦点；次要动作不遮挡主内容；
- 相邻镜头的构图、入场和节奏没有连续机械重复。

这些检查只能报告可观察缺陷，不能给审美分数，也不能用“lint 通过”宣布创作通过。用户仍负责代表镜头和整条 preview 的审美选择。

## 7. HyperFrames / Remotion 对齐

### 已确认的问题

- 2026-08-17 实测被显式强制为 HyperFrames，全 20 镜不能用于判断 auto 路由质量。
- 20 份 Recipes 的能力标签几乎相同；若真正执行 auto，粗粒度矩阵可能又把全片统一导向一个后端，而不是按内容选择。
- 现有 Remotion 验证覆盖路由、schema、依赖版本和 DOM trace，但没有一条新生产路径的真实 `Composition → typecheck → CLI render → FFprobe/full decode → shot contract → preview` 端到端证据。
- HyperFrames 有随 release 固定的运行时；Remotion 依赖现有项目本地同时安装匹配的 `remotion` 和 `@remotion/cli`，实际可用性不对称。
- 当前安装器和 readiness cache 只准备 HyperFrames；Remotion 新项目却在 Builder 开工前就要求已经存在精确依赖、lock、安装和 CLI，形成“先有项目才能预检、通过预检才能创建项目”的循环。
- 没有强证据时矩阵最终仍回落 HyperFrames；Remotion pattern 证据权重又低于常见的 HyperFrames DOM/CSS 证据，Shotcraft pattern 还是可选命中，因此实际路由长期偏斜。

### 本 PR 要求

1. Director 必须为每镜写内容相关、可解释的能力需求；禁止所有 Recipes 无脑复制同一能力集合。
2. `auto` 的路由记录每镜选择原因和被拒绝后端，不允许只有最终 backend。
3. 显式选择仍可强制整片单后端，但 benchmark 必须标成 forced，不能写成 auto 结果。
4. 发行包要么提供可运行的 Remotion 基线项目和固定版本工具链，要么把公开支持状态改为“仅适配已有 Remotion 项目”，不能维持未经实证的完整双后端承诺。
5. 后端失败返回原后端修复，不允许静默改路由。
6. Remotion license、依赖准备和工具链身份每个 production root 只处理一次；一个 unit 一次 typecheck、一次 bundle，多条 Composition 分别直渲染，不能按 shot 重复安装和打包。

### 必须新增的真实测试

- **HyperFrames canary**：至少 3 个不同内容关系的 shot，按新合同直渲染并装配 preview。
- **Remotion canary**：至少 3 个不同内容关系的真实 Composition，完成 typecheck、CLI render、逐 shot 合同、完整解码和 preview 装配。
- **同 SRT true-auto**：不传 `--runtime`，保存逐镜头选择理由；自然只选一个后端也可以，但不能人为制造 hybrid。
- **同 SRT forced-remotion**：完整约 180 秒生产，记录真实耗时、失败和输出；完成前 README 不能说 Remotion 与 HyperFrames 已被同等验证。

## 10. 验收标准

### 自动合同

- 所有现有相关测试通过，并新增角色注入、最小任务包、禁止自建工具、shot 直出和 Remotion canary 测试。
- production child 对父 Skill、其他阶段 Skill 和三份通用 craft reference 的读取次数为 0。
- 自建 capture/trace/verify 脚本数量为 0；默认 dense/full-frame trace 次数为 0。
- shot 文件数严格等于 Recipe 数，全部独立完整解码，preview 只能从这些 shot 文件装配。
- Lead 三条样片至少覆盖三种内容关系/构图/节奏，不能只换文字。
- 任何 lint 都不能因稳定停留失败，也不能建议添加无意义运动。

### 同一 179.866 秒 SRT 实测目标

| 指标 | v1.0.0 基线 | v1.0.1 必须达到 |
| --- | ---: | ---: |
| Lead | 62.90 分钟 | `≤35` 分钟 |
| production Builders 并行阶段 | 88.14 分钟 | `≤55` 分钟 |
| Director 开始到第一版完整分段 preview | 242.05 分钟 | `≤120` 分钟 |
| 子 Agent 自建检查工具 | 至少 2 次 | `0` |
| 默认逐帧/高密度全镜扫描 | 已发生 | `0` |
| 最终直接渲染 shot 文件 | 0 | 等于全部 Recipes |

Token 仍只能记录宿主可取得的真实值，不能估算。若宿主能提供，目标是子 Agent non-cached input 较 v1.0.0 同阶段下降至少 40%；若不能取得则记 `unknown`，不宣称通过。

### 视觉底线

- 无文字/图形覆盖主内容，无元素只进不出，无旧信息积压。
- 一个时刻一个主要焦点；次要动作不抢戏。
- 每镜存在可读结果与稳定结尾；静止不被当成缺陷。
- 相邻镜头不连续复用同一构图、入场和节奏。
- 不因 lint 添加永久漂浮、呼吸、循环或轻微抖动。
- 三条代表镜头、全部 6 格检查图和整条 preview 可供用户快速判断；自动检查不得代替用户审美。

## 11. 实施顺序

1. 先写失败测试：禁止自建证据工具、零重复必读、shot 数量/直渲染、静止合法、Remotion E2E。
2. 改 role charter 注入和最小 assignment packet。
3. 改统一 render/check/contract 脚本，把机械工作从 Lead / Builder 移给 Parent。
4. 改 shot-native schema、assembler 和 legacy shot-export。
5. 修 motion lint 的错误激励和 Lead 全片动画地图。
6. 完成 HyperFrames / Remotion canary，再跑同 SRT true-auto 与 forced-remotion。
7. 最后跑同一 179.866 秒实测；没有达到时间、分段直出和视觉底线，不得发布。

## Definition of Done

只有同时满足以下条件才可合并：

- Lead / Builder 不再建立检查工具或证明自己通过；
- 子 Agent 不再重复读取通用规则文件，角色硬规则被自动注入并在制作前重锚；
- Lead 输出三种真正不同的代表表现，不提供整镜头填空模板；
- 全部最终镜头由各自源码直接分段渲染，整条 preview 由这些镜头装配；
- HyperFrames 与 Remotion 的支持范围有真实 E2E 证据或被诚实降级说明；
- 同一 SRT 第一版完整分段 preview 不超过 120 分钟；
- 用户能用代表镜头、逐镜头 6 格图和整条 preview 判断质量，且没有覆盖、积压、焦点竞争和无意义持续运动。
