# v1.0.1 修正 PR：恢复镜头创作闭环

## PR 标题

`refactor: restore shot-level creative ownership before v1.0.1 release`

## 状态

- 本文是对 `docs/V1.0.1-PR-SPEC.md` 的修正增量，不另建 v1.0.2，也不重开一套新流程。
- 当前 v1.0.1 候选实现不得按原样发布。先完成本文的 5 镜头 canary，通过后才允许跑完整约 180 秒实测。
- 若本文与上一份规格冲突，以本文为准；未冲突部分继续执行，尤其保留按镜头直接渲染、Parent 统一机械检查、Lead 和多 Builder。

## 一句话目标

让同一个 Chapter Builder 对一组连续镜头完成“理解原文与设计 → 选择表现和素材 → 制作 → 观看真实画面 → 修改”的完整创作闭环；仓库只替它处理确定性的渲染和媒体合同，不再用大量检查证据冒充视觉质量。

## 为什么当前候选版仍然失败

2026-08-18 同一份 179.866 秒、20 镜头 SRT 的真实运行说明，问题已经不是规则不够多，而是创作责任被拆散了。

### 1. `shot-native` 被错误实现成“一镜一个创作 Agent”

- 正确含义：最终媒体边界是一条语义镜头，每镜直接渲染为独立 MP4。
- 实际实现：20 条 Recipes 被拆成 20 个 authoring units；Lead 做 3 镜，另外启动 17 个 production Builders。
- 结果：每个 Builder 只知道一个局部镜头，无法控制连续段落的节奏、构图变化和相邻接力；相同的最省事结构被独立复制 17 次。
- 根因：每份 Recipe 都写入 `authoring.solo=true`，理由只是“无跨镜持续活元素或连续相机”。这不是独立创作的必要条件，却覆盖了上一份规格要求的 5–8 镜聚合。

必须重新分开三个边界：

| 边界 | 默认粒度 | 用途 |
| --- | --- | --- |
| 语义边界 | 1 shot | SRT 含义和最终媒体文件 |
| 创作边界 | 1 chapter，通常 5–8 shots | 一个 Builder 负责连续视觉叙事 |
| 检查边界 | 1 shot | 独立解码、画面抽查和合同 |

### 2. 没有人拥有完整创作上下文

原始 `SURGE-design.md` 明确要求高能量、超大字号、`surgeFlow`、`ribbonDraw`、`punch-in`、count-up 等视觉语言，但它没有进入 Lead 和 production Builder 的 assignment packet。

Director 把原始设计压成中间 JSON，Lead 再压成共享 token，Builder 最终只拿到 Recipe、共享源码和大量约束。每一层都“合规”，但原始创作意图已经丢失。Auto Motion 的 scene owner 则直接拿到完整逐字稿、完整 design、scene plan、素材和动画技能，并负责看到实际帧后修改。

### 3. 素材分支在制作前被过早关闭

本次 20 镜中有 17 镜是纯 `native-structure`，只有 1 镜用了真实图片；Pexels 和生成图片均为 0。`no-external-material.md` 在 Builder 开工前全局关闭了外部搜索和生图。

Auto Motion 在相同 SRT 和相同 design 下有 9 镜使用图片、SVG 或视频，其中包含 8 份生成素材。素材数量不是质量本身，但抽象概念、人物处境和隐喻需要可识别的视觉对象；只剩暗色 DOM 卡片时，表现空间被系统提前砍掉了。

### 4. Lead 交付的是防错骨架，不是可复用的创作能力

Lead 的共享 motion source 只有通用 progress、easing、mix、opacity 和检查 metadata，没有落实 design 指定的 signature motion，也没有图片裁切、遮罩融合、纵深和信息密度组织能力。

17 份 Builder 源码中：

- 16 份复用同一种 `StaticGlow`；
- 17 份复用同一种 `Kicker`；
- 0 份使用 `surgeFlow`、`ribbonDraw`、`punch-in`、count-up 或渐变动画；
- 只有 1 份使用真实图片。

所以 Lead 与 Builder 都花了近一小时，却没有形成“Lead 做难能力、Builder 用能力完成多样镜头”的分工。

### 5. 系统证明了可检查，没有证明好看

本次产生 18 份 runtime inspection、17 份 inspection source、94 个 trace 调用和大量 diagnostics；所有检查均通过。但检查结果自己也承认，几何轨迹不能证明故事含义、重量感、弧线、夸张或吸引力。

六格图被生成了，却没有强制原 Builder 真正观看并修改；`visual-lock` 在无人值守运行中被跳过。于是责任链变成：

```text
Director 认为 Recipe 写完了
→ Lead 认为共享源码写完了
→ Builder 认为检查通过了
→ Parent 认为合同完整了
→ 没有人对“观众看到的画面是否成立”负责
```

视觉结果也与设计目标明显冲突：实测抽样中，本版平均亮度约为 18.48，180 个秒级样本里 136 个低于 20；Auto Motion 平均约为 31.62，低于 20 的样本为 0。亮度不是审美分数，但足以证明 `energy: high` 被实现成了大面积近黑、稀疏的画面。

## 本 PR 保留什么

- 保留 Director：负责事实、语义边界、全片视觉方向和相邻镜头关系。
- 保留 Assets：负责已知共享素材、字体、授权和素材索引。
- 保留 Lead：负责把 design 变成可运行的视觉语言、signature motion 和三类真实样片。
- 保留多个 Builder：但改为 Chapter Builders，不再默认一镜一个 Agent。
- 保留 Parent 的确定性渲染、FFprobe、完整解码、hash、媒体合同和 preview 装配。
- 保留每镜独立源码入口、独立直接渲染 MP4 和后期顺序索引。
- 保留逐镜头六格语义图，但改变观看人和完成条件。
- 保留 HyperFrames / Remotion 两类适配能力，但生产默认先回到有完整创作闭环的 HyperFrames。

## 本 PR 明确删除什么

- 删除 Director 写入或决定 `authoring.solo` 的权限。
- 删除“媒体按 shot 直出，因此创作也必须按 shot 分 Agent”的隐含逻辑。
- 删除在 assignment packet 中用压缩摘要替代原始 SRT 和原始 design 的做法。
- 删除 Assets 在所有镜头完成素材判断前写入全局 `no-external-material` 结论。
- 删除 Lead / Builder 源码里的 `data-erduo-trace`、visual weight、focus group、layer 和人工 motion-window 证明字段。
- 删除每个 production unit 自带 `inspection.tsx`、通过态 diagnostics 和通过态密集轨迹产物。
- 删除“检查脚本通过即可 handoff”的完成定义。
- 删除通用能力标签驱动 production auto-routing 的默认行为。
- 删除完整 180 秒首轮实测作为开发反馈环；先过 5 镜头 canary。

## 新的默认流程

```text
Parent 读取完整 SRT + 原始 design + 用户素材
→ Director 划分 shots 和 chapters，输出事实合同与可修改创作建议
→ Planner 确定 3 个左右 authoring units，每组通常 5–8 个连续 shots
→ Assets 冻结已知共享素材，但保持“镜头专项素材”通道开放
→ Lead 制作 3 条不同类型真样片 + 共享视觉/运动/素材能力
→ 先跑 5 镜头 creative canary
→ 每个 Chapter Builder 拿到完整原文、原始 design、章节任务和真实样片
→ Builder 设计、制作、直接渲染、观看六格图/短预览并至少完成一次自审结论
→ Parent 做确定性媒体检查与逐 shot 合同
→ Parent 从已验证 shot 文件装配整条 preview
→ 用户审美选择
```

这里的“Builder 观看”不是回到逐帧检查。默认只看每镜六格图和自己的 chapter preview；发现某一动作可疑时，才看该镜的短连续帧或短视频。

## 1. Director：只冻结真相，不冻结表现形式

### Shot Recipe 拆成两层

第一层是 Builder 不得改变的 `truth`：

```json
{
  "shotId": "S05",
  "srtWindowMs": {"start": 38100, "end": 46900},
  "sourceCues": ["原始字幕 cue id"],
  "spokenFacts": ["不能改写的事实"],
  "audienceOutcome": "观众看完这镜必须明白什么",
  "requiredReadableResult": "结尾必须清楚看到什么",
  "incomingSeam": "cut|match|handoff",
  "outgoingSeam": "cut|match|handoff"
}
```

第二层是 Builder 可以在不破坏 `truth` 时重做的 `creativeProposal`：

```json
{
  "metaphor": "建议，不是命令",
  "objects": ["建议对象"],
  "composition": "建议构图",
  "motionIdea": "建议主动作",
  "materialRoute": "native|provided|search|generate|mixed",
  "keyStates": ["建议状态"],
  "whyThisCouldWork": "一句话"
}
```

Builder 可以修改 `creativeProposal`，但必须在 handoff 中用一句话记录改了什么、为什么更符合 `truth`。这不是审批流程，也不要求重新找 Director。

### Director 必须输出 chapter 建议，不能输出 solo 决定

Director 只标记：

- 语义章节边界；
- 相邻镜头的承接关系；
- 哪些镜头共享概念、素材或节奏；
- 真正需要独立技术隔离的风险标签。

`authoring.solo` 从 Recipe schema 删除。是否独立 unit 由 Planner 按确定性规则决定。

### Director 的正向创作要求

- 每镜写清观众结果，不预先锁死 DOM 结构。
- 不能给所有镜头复制同一组 capability 标签。
- 抽象概念必须判断是否需要人物、真实对象、界面证据或生成隐喻，不能默认 `native-structure`。
- 全片 motion map 只负责避免连续重复，不替 Builder 写模板。

## 2. Planner：创作按章节聚合，媒体仍按镜头直出

### 默认分组算法

1. 先按 Director 的连续语义章节分组。
2. 每个 authoring unit 目标为 5–8 个连续 shots。
3. 目标时长约 35–70 秒；不足 3 镜优先与相邻章节合并，超过 8 镜再按语义转折拆分。
4. Lead 已完成并锁定的代表镜头保留在所属 chapter 中，但直接复用，不由 Chapter Builder 重做。
5. 一条约 180 秒、20 镜头的常规任务，默认应形成约 3 个 production chapters，而不是 20 个 units。

### 仅以下情况允许 solo unit

- 需要独占且无法与同 unit 共存的 3D / WebGL / GPU 状态；
- 需要独立外部工程或独立运行时工具链；
- 单镜自身超过 35 秒且内容确实构成完整章节；
- Parent 检测到明确的资源或依赖冲突。

“无跨镜持续活元素”“没有连续相机”“媒体需要单独 MP4”都不是 solo 理由。

### 必须新增的 Planner 断言

- `authoringUnits < shotCount`，除非每个 solo 都命中允许原因。
- 常规 15–24 镜输入的 unit 中位数必须在 5–8 镜范围。
- `integrationMode=shot-media` 不得改变 authoring grouping。
- Planner 输出每个 unit 的 `groupingReason` 和每个 solo 的枚举型 `soloReason`，不接受自由文本绕过。

## 3. Chapter Builder：恢复完整创作所有权

### 每个 Builder 必须收到的 assignment packet

1. 完整原始 SRT，而不是只有本镜摘要；
2. 完整原始 design 文件，原文保留，不由 Director 二次概括替代；
3. 本 chapter 的 `truth` 和 `creativeProposal`；
4. 前一镜、后一镜及章节边界的 seam 信息；
5. Lead 的 3 条真实样片、共享源码和“哪些能力可复用”的短索引；
6. 已知素材索引、授权状态和可用字体；
7. 允许使用的镜头专项素材入口：现有素材、检索、生图或混合；
8. 当前选定运行时的最小制作命令和 motion-graphics 正向创作规则；
9. 输出路径、渲染命令和失败时的最小修复信息。

不要再次要求 Builder 阅读父 Skill、其他阶段 Skill、完整 schema、validator、lint 源码和多份通用 references。原始 design 和 SRT 是任务事实，不属于应该被“去重”掉的规则文件。

### Builder 的职责

- 对 chapter 内的构图变化、节奏和相邻承接负责。
- 可以推翻 `creativeProposal`，不能改 `truth`。
- 为每镜主动选择表现形式和素材路线；不能因为共享组件存在就套同一模板。
- 使用 Lead 的视觉语言和运动能力，但不必复用 Lead 的整体布局。
- 完成源码后直接渲染每条 shot，查看六格图和 chapter preview。
- 至少写一条真实自审结论：`accepted` 或 `revised`；若 revised，记录实际改动，不提交观看感想长文。

### Builder 的完成条件

只有同时满足以下条件才算完成：

- 本 chapter 每条 shot 都有独立直接渲染文件；
- Parent 技术检查通过；
- Builder 已实际打开六格图或 chapter preview；
- 没有低级视觉错误；
- chapter 内相邻镜头不是连续同构模板；
- `truth.requiredReadableResult` 在结果帧中可读；
- 所用素材进入索引并保留来源信息。

“trace 通过”“diagnostics 已生成”“无 lint 报错”不能单独构成完成。

## 4. Lead：交付真实能力，不交付填空模板

Lead 继续存在，但只做能显著降低 Chapter Builder 难度的工作。

### Lead 必须直接读取

- 完整原始 SRT；
- 完整原始 design；
- Director 的全片 motion map；
- 三条代表镜头的 Recipe；
- 已知共享素材和字体。

### Lead 必须交付

1. 三条内容关系明显不同的真实代表镜头：
   - 一条以原生图形和文字为主；
   - 一条以真实或生成素材融合为主；
   - 一条信息密度较高、包含界面/流程/数据组织的镜头。
2. Design 指定的 signature motion。如果 design 明确写了 `surgeFlow`、`ribbonDraw`、`punch-in`、count-up，就必须至少在样片或共享能力中真实运行，不能只改名登记。
3. 素材能力：图片裁切、遮罩、景深/层次、背景融合和必要的来源绑定。
4. 运动能力：预备、主动作、跟随/重叠、落定和可读停留的可组合原语。
5. 一页以内的能力索引：说明“适合什么内容关系”，禁止提供一份换字即可复用的整镜头模板。

### Lead 不再交付

- trace schema；
- inspection 页面；
- 手工 motion windows；
- 每帧 visual weight / focus group / layer 证明；
- 通过态 diagnostics；
- 为证明自己看过规则而写的总结。

### Lead 验收

- 三条样片必须能从 silhouette、构图和主动作上被快速区分，不能只换文案。
- 至少一条样片使用真实或生成素材，除非用户明确禁止所有外部/生成素材。
- 原始 design 中的核心能量、字号层级和 signature motion 有可见证据。
- 样片通过后直接成为对应 shots 的最终源码，不交给后续 Builder 重写。

## 5. Assets：冻结已知素材，不关闭创作可能性

Assets 阶段只负责：

- 盘点用户提供素材；
- 找到跨镜共享素材；
- 处理字体和授权；
- 建立素材索引和可复用衍生文件；
- 标记明显缺口。

Assets 阶段不得根据 Director 的初稿，为整部片写入不可逆的 `no-external-material`。每条 shot 必须保留以下一种路线：

```text
native
provided
search
generate
mixed
```

Chapter Builder 可以在制作时把 `native` 改为 `search`、`generate` 或 `mixed`，只需记录一句原因和素材来源。只有以下情况才全局关闭搜索/生图：

- 用户明确禁止；
- 当前环境完全不可用；
- 授权或费用边界不允许。

关闭时必须写明真实原因，不能写成创作判断。

## 6. 动画规则：从“禁止犯错”改成“先建立正向动作”

角色注入继续保留十二原则的可执行转译，但 Builder 制作前的短锚点必须同时包含正向要求：

1. **Staging**：先让观众知道看哪里，再发生变化；一拍一个主焦点。
2. **Anticipation**：重要变化前给短准备信号，但小 UI 变化不机械弹跳。
3. **Straight Ahead / Pose to Pose**：信息镜头先定 opening、turn、result、settle；有机细节可在关键姿态间自然发展。
4. **Follow Through / Overlap**：附属对象由主动作带动，稍晚结束，最后必须停下。
5. **Slow In / Slow Out**：速度变化服务重量和可读性，不统一套同一 easing。
6. **Arcs**：有机对象和镜头运动优先弧线；机械界面保持有意的直线和裁切。
7. **Secondary Action**：只能加强主意图，不能形成第二焦点。
8. **Timing**：按语义、阅读量、重量和情绪分配时间；稳定停留合法。
9. **Exaggeration**：每镜选一个最重要变化适度放大，不让所有元素同时夸张。
10. **Solid Drawing / Spatial Coherence**：保持体积、锚点、遮挡和层级一致，避免悬空连接线与无承载容器。
11. **Appeal**：必须有清楚的形状层级、对比、材质或可识别对象；“无报错”不等于有吸引力。
12. **Squash and Stretch**：只用于适合变形的对象，并保持体积感；文字、Logo、硬 UI 默认不挤压。

每镜不必机械使用十二条。Recipe 至少选出 2–4 条真正相关的 `craftIntent`，Builder 在真实画面里落实；这些字段是创作提示，不做逐条打分或 trace。

## 7. 观看与修改：六格图必须进入创作循环

### 默认观看责任

- 原 Builder 看自己每镜六格图和一条 chapter preview。
- Lead 看三条代表镜头的六格图和短预览。
- Director 不回看全片动态，不承担最终逐镜审片。
- Parent 只判断确定性问题，不给审美分。
- 用户只需要看 5 镜头 canary、Lead 代表镜头和最终整条 preview。

### 六格图检查内容

- opening 是否已经泄露最终答案；
- preparation 是否清楚且不过度；
- action-a / action-b 是否出现覆盖、瞬移、悬空连接或状态积压；
- result 是否准确表达 `requiredReadableResult`；
- settle 是否稳定、可读且没有无意义循环；
- 相邻镜头是否连续复用同一构图和入场。

### 低级错误必须修改，不能只记录

- 文字、卡片、线条或图片遮挡主内容；
- 新旧状态同时堆叠且没有语义；
- 元素只进不出，结尾残留无关对象；
- 空框、空胶囊、无终点连接线；
- 字号不可读、整页截图缩成小卡片；
- 主动作未落定就开始下一组动作；
- 画面与 design 的能量、明暗或密度明显相反；
- 同 chapter 连续三镜使用同一 layout skeleton、entry 和 rhythm。

Builder 如发现问题，只重渲染对应 shot；不升级为全片逐帧扫描。

## 8. 检查系统瘦身

### Parent 继续自动检查

- 文件存在、时长、帧数、分辨率、fps、codec；
- FFprobe、完整解码、hash、source identity；
- shot 数量、顺序、SRT 覆盖和 direct-runtime-render 合同；
- 黑帧/近空画面、越安全区、明显遮挡和缺字体等粗粒度底线；
- 六格图与 chapter preview 生成。

### 从生产源码和通过态输出中删除

- `data-erduo-trace*`；
- `visualWeight`、`focusGroup`、`layer` 等证明字段；
- 人工声明的 motion windows；
- unit 私有的 `inspection.tsx`；
- 成功时的逐帧轨迹、密集 JSON 和 diagnostics 目录；
- “为了证明画面持续发展”而添加的 motion lint。

失败时可以保留最小证据：`shotId + 时间窗口 + 问题类型 + 一张图或短日志`。修复后成功 receipt 只保留一行结果和媒体身份。

### 自动检查不得宣称

- 画面有吸引力；
- 隐喻成立；
- 动作有重量感；
- 十二原则落实；
- 用户会喜欢。

这些只能由拥有上下文并看过真实画面的 Builder、Lead 或用户判断。

## 9. Runtime 策略：先恢复质量，再开放自动路由

当前 generic capability routing 把 19/20 镜都贴上相同能力标签，并因 `motion.frame-driven-multiphase` 的优先级把全片导向 Remotion。这不是内容判断。

v1.0.1 的发布策略改为：

- `production default = hyperframes`；
- `remotion = explicit opt-in | canary`；
- `auto = experimental`，不作为默认生产入口；
- README 和支持矩阵必须如实标注，直到 Remotion 达到相同创作与交付闭环。

这不是删除 Remotion。Remotion 仍需完成真实 `Composition → typecheck → CLI render → FFprobe/full decode → shot contract → preview` E2E，但不能因为技术链跑通就自动接管全片。

重新开放 production auto 的必要条件：

1. capability 必须描述镜头真实需求，不能复制通用集合；
2. 每个后端都有同等 assignment packet、原始 design 和素材能力；
3. 同一 5 镜头 canary 中，Remotion 的视觉结果不弱于 HyperFrames；
4. route 失败不静默换后端；
5. 用户明确选择 auto 或默认策略经真实 A/B 验证。

## 10. 先做 5 镜头 creative canary

在运行完整约 180 秒任务前，只制作以下 5 类镜头。若当前 SRT 编号改变，按内容类型选择等价镜头：

| 镜头 | 主要检验 |
| --- | --- |
| S01 抽象因果 | 能否用一个强主动作建立概念，而不是暗色卡片堆叠 |
| S05 生成素材隐喻 | 生图/素材融合是否真正进入创作闭环 |
| S07 高密度上下文 | 真实界面、信息层级和聚焦是否可读 |
| S09 对象变形 | anticipation、主动作、follow-through、settle 是否成立 |
| S15 流程/事实板 | 多步骤信息是否有因果顺序而非同时堆满 |

### Canary 对照方式

- 输入必须与 Auto Motion 对照一致：同一 SRT、同一原始 design、同一用户素材权限。
- 我方 Builder 允许使用可用的图片生成和素材检索能力，不能人为少给创作材料。
- 先产出我方 5 镜头，不要求 Auto Motion 迁就我方 schema。
- 交给用户盲看或至少不显示实现信息，只回答“更愿意采用哪一版”和最明显问题。
- 若用户仍能立即选出 Auto Motion，停止完整生产，先修 canary；不得用跑完全片增加沉没成本。

### Canary 硬门槛

- 5/5 独立 shot 均直接渲染并完整解码；
- 5/5 Builder 已看六格图或短 preview；
- 0 个覆盖、积压、悬空线、空容器、不可读结果等低级错误；
- 至少 3 种明显不同的 composition family；
- 至少 2 镜使用真实或生成素材，除非输入确实不需要且用户认可；
- 原始 design 的字号层级、能量和至少 2 种 signature motion 可见；
- 用户选择我方不少于 3/5，且剩余镜头差距可由明确局部修改解决；
- 从 assignment 发出到 5 镜头第一版 preview 的 wall time `≤45 分钟`。

用户选择是发布门槛，不用自动评分替代。若不方便盲评，至少保存用户逐镜采用/不采用结论。

## 11. 完整实测门槛

Canary 通过后，才运行同一 179.866 秒、20 镜头任务。

### 流程与交付

- 常规 authoring units 约为 3 个，不得再次变成 20 个；
- 每 unit 通常 5–8 个连续 shots；
- production Builders 数量与 unit 数量一致，不再启动 17 个单镜 Builder；
- 最终 20 条 shot 均从运行时源码直接渲染，不从 master 二次切割；
- preview 只从已验证 shot 文件装配；
- Lead 样片直接复用，不重做；
- 子 Agent 新建检查/证明工具数量为 0。

### 时间目标

| 阶段 | 2026-08-18 候选版 | 修正后门槛 |
| --- | ---: | ---: |
| Director | 56分31秒 | `≤25 分钟` |
| Lead | 54分17秒 | `≤30 分钟` |
| production Builders 并行墙钟 | 1小时03分13秒 | `≤45 分钟` |
| 第一版完整分段 preview | 3小时23分13秒 | `≤100 分钟` |

时间不能靠降低分辨率、跳过完整解码、减少 shot 或复用同一模板达成。Token 只记录宿主真实值；不可取得就写 `unknown`，不估算。

### 视觉门槛

- 用户不再能因“整片近黑、稀疏、同模板”立即判定 Auto Motion 完胜；
- chapter 内连续镜头有明确的构图、素材和节奏变化，同时保持同一 design 世界；
- design 明确要求的高能量、超大字号和 signature motion 可见；
- 需要人物、对象、界面证据或隐喻的镜头不被系统默认压成纯 DOM 卡片；
- 六格图中没有覆盖、积压、焦点竞争和无意义持续运动；
- 最终仍由用户整条 preview 审美确认，自动检查不代替用户。

平均亮度只能作为本次 `energy: high` 设计的异常报警，不设成通用风格阈值。对于本 canary，可加入“近黑/近空占比不得显著劣于已批准样片”的同项目比较，避免把深色设计误判为错误。

## 13. 必须先写的失败测试

1. **Grouping test**：20 shots 的正常 fixture 不能生成 20 units，且每个非 solo unit 为连续 5–8 shots。
2. **Solo authority test**：Recipe 出现 `authoring.solo` 必须校验失败；Planner 只接受枚举型 solo 原因。
3. **Boundary separation test**：`integrationMode=shot-media` 下仍为 chapter units，但最终媒体数量等于 shot 数。
4. **Packet completeness test**：Lead / Builder packet 必须含原始 SRT 和原始 design 的 identity 与可读路径，不能只有摘要。
5. **Creative freedom test**：Builder 可以修改 `creativeProposal`，但修改 `truth` 必须失败。
6. **Material reopening test**：Assets 的 shared freeze 不得阻止单镜从 `native` 改成 `generate/search/mixed`。
7. **Lead capability test**：design 声明 signature motion 时，Lead manifest 必须绑定真实可运行实现和至少一条样片使用记录。
8. **No proof artifacts test**：production source 出现 trace metadata、unit inspection source 或通过态 dense diagnostics 必须失败。
9. **View-loop test**：没有 Builder `accepted|revised` 观看回执时，chapter 不能 handoff；回执不得要求长篇报告。
10. **Canary gate test**：5 镜头视觉 gate 未通过时，Parent 不得启动 full production。
11. **Runtime policy test**：默认 production 选择 HyperFrames；Remotion 和 auto 只有显式模式才能启用。
12. **Direct delivery test**：所有 shot 合同仍必须是 `direct-runtime-render`，preview 只能引用这些文件。

## 14. 实施顺序

1. 写上述失败测试，先锁住创作边界、上下文和素材权限。
2. 删除 Director 的 solo 决策，修 Planner 的 chapter grouping。
3. 改 assignment packet，让原始 SRT/design 和 Lead 真样片直接到达创作者。
4. 改 Assets 的 material freeze，开放 shot-specific 搜索/生图。
5. 重写 Lead 交付合同和 Chapter Builder 完成定义。
6. 删除 trace / inspection / pass diagnostics 生产要求，保留 Parent 的确定性媒体检查。
7. 把 production 默认切回 HyperFrames，并诚实降级 auto/Remotion 文档状态。
8. 只跑 5 镜头 canary；未通过就迭代，不跑全片。
9. Canary 通过后跑同一 179.866 秒完整实测，记录真实时间、Token、目录体积、逐镜用户选择和交付合同。

## Definition of Done

只有同时满足以下条件才可合并和发布 v1.0.1：

- 20 镜头不再产生 20 个创作 units，常规任务按约 3 个 chapter 并行制作；
- 原始 SRT 和原始 design 不经压缩替代，直接进入 Lead 和 Chapter Builder 上下文；
- 每个 Chapter Builder 能选择/生成镜头专项素材，并对真实画面完成一次观看—修改闭环；
- Lead 交付三类可区分真样片、design signature motion 和素材融合能力，不交付填空模板；
- production 源码与通过态输出不再包含 trace/inspection 证明系统；
- 每镜仍由自己的运行时源码直接渲染成独立最终 MP4；
- 5 镜头 canary 通过用户选择、低级错误、表现多样性和 `≤45 分钟`门槛；
- 完整同 SRT 第一版分段 preview `≤100 分钟`，且没有近黑稀疏、全片同模板、覆盖、积压和焦点竞争；
- Remotion/auto 的公开状态与真实证据一致，不再用技术合同通过冒充视觉生产能力；
- 用户看完实际 preview 后认可质量达到可继续发布和迭代的底线。

## 可直接粘贴的 PR 描述

### What

This PR corrects the v1.0.1 implementation after the 2026-08-18 same-SRT production run. It preserves shot-native direct delivery, Parent-owned deterministic media checks, Lead, and parallel Builders, but restores an end-to-end creative loop for each chapter.

### Why

The candidate run converted 20 shots into 20 authoring units, withheld the original design from Lead/Builders, closed material generation before building, and produced extensive passing inspection evidence without a creative owner viewing and revising the actual result. The output was technically valid but visually sparse, repetitive, and far behind the Auto Motion comparison.

### Changes

- group normal work into 5–8-shot contiguous chapters while keeping one directly rendered MP4 per shot;
- split immutable Recipe truth from revisable creative proposals;
- pass the full original SRT and design directly to Lead and Chapter Builders;
- keep shot-specific search/generation open after shared asset freeze;
- require Lead to deliver three distinct real samples, signature motion, and material-fusion capabilities;
- require the original Builder to view six-frame sheets/chapter preview and revise actual defects;
- remove production trace metadata, inspection source, and passing diagnostics proof work;
- temporarily make HyperFrames the production default and mark Remotion/auto as explicit canary modes;
- block full production until a five-shot creative canary passes user preference, visual-baseline, and time gates.

### Validation

- grouping, solo authority, packet completeness, material reopening, no-proof-artifacts, view-loop, runtime-policy, and direct-delivery tests;
- five-shot same-input A/B canary before any full run;
- full same-SRT run only after canary approval, with `≤100 min` first segmented preview and user review of the actual output.
